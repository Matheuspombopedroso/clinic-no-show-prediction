## What problem it solves

A clinic system (scheduling screen, reminder job) needs a probability for one
appointment *right now*, or for a whole day's agenda at once. The service has
to answer fast, use CPU efficiently when many single requests arrive at the
same time, and scale out by adding processes.

## Layers

```
HTTP ──► Ray Serve proxy ──► NoShowDeployment replica (×N)
                                 │  FastAPI ingress (validation, OpenAPI)
                                 │  @serve.batch for /predict
                                 ▼
                          PredictionService  (pure Python, no Ray)
                                 │  build_features → XGBoost → risk rules
                                 ▼
                          NoShowModel (versioned artifact)
```

- **`PredictionService`** holds all the logic. It has no Ray or HTTP code, so
  it is unit-tested directly and reused unchanged by the plain FastAPI app in
  `api.py`, which the API tests use.
- **`NoShowDeployment`** is a thin Ray Serve wrapper. It adds replication and
  dynamic batching.

## Endpoints

| method | path | body | notes |
|---|---|---|---|
| GET | `/health` | – | status + model version |
| POST | `/predict` | one `Appointment` | goes through `@serve.batch` |
| POST | `/predict/batch` | `{"appointments": [...]}` (1–1000) | one vectorised model call |
| GET | `/docs` | – | OpenAPI UI generated by FastAPI |

Response for `/predict` (one element of `predictions` for `/predict/batch`):

```json
{
  "appointment_id": "apt-1",
  "no_show_probability": 0.38305,
  "risk_level": "medium",
  "recommended_action": "Request explicit confirmation (SMS/WhatsApp) 48h before the appointment.",
  "model_version": "1.0.0",
  "inference_time_ms": 23.284
}
```

(This is a real response from the 2-replica deployment, for the `curl`
example at the end of this page. It was the first request after start-up, so
`inference_time_ms` is higher than in steady state.)

## Dynamic batching (`@serve.batch`)

```python
@fastapi_app.post("/predict", response_model=Prediction)
async def predict(self, appointment: Appointment) -> Prediction:
    return await self._predict_batched((appointment, time.perf_counter()))


@serve.batch(max_batch_size=32, batch_wait_timeout_s=0.005)
async def _predict_batched(self, items):
    appointments = [a for a, _ in items]
    start_times = [t for _, t in items]
    return self.service.predict_with_start_times(appointments, start_times)
```

Each caller awaits `_predict_batched` with a *single* item. Serve queues
concurrent calls. When the queue holds `max_batch_size` items, or the first
item has waited `batch_wait_timeout_s`, Serve calls the method once with the
whole list and sends each caller its own result. Feature building plus the XGBoost
call has a fixed cost that barely changes between 1 and 50 rows (1.419 ms vs
2.343 ms in the micro-benchmark), so one call for 32 queued requests is much cheaper than 32
separate calls. Whether that saving shows up end to end depends on where the
bottleneck is. On the benchmark machine it mostly did not (see
[benchmarks.md](benchmarks.md)).

The batch parameters are set from configuration in `__init__`, using
`set_max_batch_size` and `set_batch_wait_timeout_s`. The decorator values are
only defaults.

The trade-off is that under light load a lone request waits up to
`batch_wait_timeout_s` (5 ms by default) for others that never arrive. That
time is included in its `inference_time_ms`.

`max_ongoing_requests` (per replica) is forced to be ≥ `max_batch_size`.
Otherwise a replica would never hold enough concurrent requests to fill a
batch.

## What `inference_time_ms` measures

Server-side wall time inside the replica, from the moment the route handler
receives the parsed request until the prediction objects are built:

- `/predict`: includes the time spent waiting in the batch queue, feature
  building and the model call.
- `/predict/batch`: feature building and the model call for the whole batch.
  The same value is reported on every element and at the top level.

It does **not** include HTTP parsing in the proxy, the hop from proxy to
replica, or JSON serialisation of the response. Client-observed latency, as
reported by the load tests, is always higher.

## Horizontal scaling

`num_replicas` (env `NUM_REPLICAS`, YAML `num_replicas`) sets how many
processes each load their own copy of the model. Each replica reserves one
logical CPU (`ray_actor_options={"num_cpus": 1}`), and XGBoost is pinned to
`nthread=1` (`MODEL_THREADS`). This way, parallelism comes from replicas
rather than from threads inside one process, which keeps the 1-vs-N
comparison fair. All replicas sit behind one Serve HTTP proxy per node, and
on a single machine that proxy can itself become the bottleneck (see the
benchmarks).

## Risk levels and actions

Defined in [`risk.py`](../src/noshow/risk.py). Lower bounds are inclusive and
covered by boundary tests in `tests/test_risk.py`.

| risk_level | probability | recommended_action |
|---|---|---|
| `low` | `< 0.20` | Send the standard automatic reminder. |
| `medium` | `0.20 ≤ p < 0.45` | Request explicit confirmation (SMS/WhatsApp) 48h before the appointment. |
| `high` | `≥ 0.45` | Call the patient to confirm and consider offering the slot to the waitlist. |

Why these values: the synthetic no-show rate is about 22%, so 0.20 separates
"at or above the average patient" from "below it". 0.45 is roughly twice the
base rate. On the test set, the top decile of predictions has an observed
no-show rate above 50% (see [03-training.md](03-training.md)). These are demo
values. A real clinic would choose them from the cost of an empty slot versus
the cost of a phone call. They are not a clinical recommendation.

## Run just this part

```bash
# Option A: env-driven
NUM_REPLICAS=2 python -m noshow.serve_app

# Option B: Ray Serve config file
serve run serve_config.yaml

# Option C: without Ray (single process, same routes)
uvicorn noshow.api:app --port 8000
```

```bash
curl -s localhost:8000/predict -H 'content-type: application/json' -d '{
  "appointment_id": "apt-1", "booked_at": "2025-03-03T09:00:00",
  "scheduled_at": "2025-03-10T14:30:00", "confirmed": false,
  "prior_appointments": 4, "prior_no_shows": 2, "prior_cancellations": 0,
  "days_since_last_visit": 60}'
```

The integration test starts a real 2-replica Serve app and checks that 64
concurrent `/predict` calls each get their own answer, identical to
`/predict/batch` for the same rows:

```bash
pytest -m integration -q
```
